writeup-linux

2026-09-27 · CTF Bugku Misc

📌 题目信息

  • 题目名： linux
  • 题目平台： Bugku CTF（平台题）
  • 题目类型： MISC / 文件系统取证 + Linux 基础
  • 题目描述： linux 基础问题
  • 题目附件： linux.zip → 里面是 1.tar.gz → 解压得到 test/flag（14.7MB 的大文件）
  • 涉及工具： Linux 命令（mount / find / grep）、Python、strings

💥 解题过程

  1. 层层解压：linux.zip → 1.tar.gz → test/flag。得到一个 14786560 字节、名叫 flag 的文件。
  2. 用十六进制看一眼开头：全是 00，但中间（偏移 1024 处）开始有数据，而且能看到 /media/test、lost+found、.Trash-0、flag.txt、game 这样的字符串 → 这是一个 Linux 文件系统镜像（ext 系列）。
  3. 既然有 lost+found 和 .Trash-0（回收站），说明这题考的是"在文件系统里找文件"。有两种解法：
    • Linux 下挂载（最正统）： 
      mkdir /mnt/test
mount -o loop flag /mnt/test
ls -la /mnt/test
find /mnt/test -type f | xargs grep -a "key{"
    • 不挂载，直接搜（Windows 上也能做）：文件系统里文件内容还是原样的，所以直接用 grep -a / Python 搜关键字即可。
  4. 我用 Python 直接在整个镜像里搜 key{，找到三处： 
    偏移 8914944: key{}
偏移 8915968: key{}
偏移 8916992: key{feb81d3834e2423c9903f4755464060b}
    前两个 key{} 是空的（文件被清空/残留的空数据块），只有最后一个带着内容。
  5. 所以 flag 是：key{feb81d3834e2423c9903f4755464060b}。提交通过。

📝 收获

这道题的考点

"Linux 基础问题"背后其实是文件系统镜像取证：给你一个磁盘镜像，让你在里面找目标文件。

原理：为什么"没挂载"也能搜到 flag

  • 文件系统镜像 = 把某个磁盘分区原样复制出来的一个文件。它内部的结构（超级块、inode 表、数据块）和真实磁盘一模一样。
  • 既然文件内容就在数据块里，那么"按字节搜关键字"当然能搜到——这也是取证里最常用的第一招：strings / grep -a 大法。
  • 反过来，能挂载的话更直观：可以看到完整目录树、时间戳、权限，甚至能恢复被删除的文件（这就是 lost+found 和 .Trash-0 出现的原因）。

可复用的思路（下次遇到同类题）

  1. 先 file 文件名 判断类型；不是纯文本就直接看十六进制头。
  2. 看到一堆 00 加中间有数据的超大文件 → 大概率是磁盘/文件系统镜像。
  3. 第一招：strings 镜像 | grep -i -E "flag|key"（Windows 上可用 Python 版的 strings 实现）。
  4. 第二招：Linux 里 mount -o loop 挂载后浏览；或者用 debugfs 交互式查看 ext 文件系统。
  5. 第三招：binwalk / foremost 分离镜像里的嵌入文件。

延伸知识

  • 常见镜像类型：ext2/3/4（Linux）、NTFS/FAT（Windows）、ISO（光盘）、以及各种 CTF 里自造的格式。
  • Linux 基础命令：ls 看目录、cat 看内容、find 找文件、grep 搜内容、mount 挂载——这题名字叫"linux 基础问题"，考的就是这些。
  • grep -a 里的 -a 表示"把二进制文件当文本处理"，少了这个参数 grep 会直接说"binary file matches"而不显示内容。

防御视角

磁盘镜像是最容易泄露数据的载体：删除文件只是"把 inode 标记为可用"，数据块往往还留在原地——这就是为什么专业的数据销毁要做多次覆写，也是取证/应急响应的基础。

踩坑提示

  • 镜像里出现 key{} 这种"空的 flag"很正常（比如文件被清空过），别看到第一个就以为找到了。
  • 在 Windows 上直接双击打不开这种镜像，别以为是文件坏了。
